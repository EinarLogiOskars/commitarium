# Security policy

Commitarium runs AI coding agents against your source code on your own machine.
Its security properties are documented in [the threat model](docs/threat-model.md);
this page covers what is supported, how to report a vulnerability, and what we
consider a vulnerability in the first place.

## Supported versions

Commitarium is pre-1.0. Only the most recent release receives security fixes.

| Version | Supported |
| --- | --- |
| Latest release | Yes |
| Any earlier release | No — upgrade |

The desktop application and the service images are versioned together. A fix
means a new tag for both. See [the release guide](docs/releasing.md).

Supported host and Docker versions are listed in
[the support matrix](docs/support-matrix.md).

## Reporting a vulnerability

Report privately through GitHub's
[private vulnerability reporting](https://github.com/EinarLogiOskars/commitarium/security/advisories/new)
on this repository.

Please do not open a public issue, pull request or discussion for a suspected
vulnerability, and please do not post proof-of-concept exploits publicly before
a fix is released.

A useful report includes:

- what an attacker gains, and what access they need to start;
- the affected version, host OS, and Docker/Compose versions from
  **Settings → Runtime**;
- reproduction steps, and a proof of concept if you have one.

What to expect:

- acknowledgement within 5 working days;
- an assessment, including whether we agree it is in scope, within 10 working
  days;
- a fix in the next release for confirmed issues, or an explanation of the
  timeline if it needs longer.

This is a small project without a bounty programme. Credit is given in the
advisory unless you ask otherwise.

## In scope

Anything that breaks a boundary the design promises to hold:

- **Network exposure.** The coordinator API reachable from outside the local
  machine, or a route that should require authentication and does not.
- **The Tauri IPC boundary.** The renderer influencing which Docker volumes,
  containers, images, mounts or commands the trusted Rust layer acts on. The
  renderer is only ever allowed to supply values the backend validates against
  a fixed set — a path from renderer input to arbitrary host or Docker
  execution is a vulnerability.
- **Provider credentials.** Subscription tokens, API keys or native provider
  transcripts leaving their per-role profile volume — through IPC events, logs,
  a backup archive, another role's worker, or a project workspace. Role
  separation is a security boundary: one provider role reaching another role's
  credentials counts.
- **Repository protection.** Bypassing the Forgejo default-branch workflow, the
  required approval, or the coordinator identity requirement for a merge.
- **Validation isolation.** Escaping the isolated validation environment onto
  the host, or into another project's state.
- **Backup and restore.** Path traversal out of the restore target, skipping
  the format-version, component or SHA-256 checks, or an ordinary backup that
  contains provider credentials. The format is defined in
  [ADR-011](docs/adr/0011-use-a-versioned-credential-free-directory-backup.md).
- **Internal secrets.** Coordinator-to-worker tokens or Forgejo credentials
  readable by something that should not have them, or written somewhere they
  outlive their intended scope.
- **Supply chain.** A compromised or misattributed release artifact, or a
  published image that does not match the tagged source.

## Out of scope

These are documented design decisions, not flaws. Reporting them will get you
a link back to this section.

- **An agent writing bad, insecure or wasteful code inside its own workspace.**
  That freedom is the point of the product; the boundary is that it cannot
  escape the workspace or merge without your approval. See "Intended worker
  freedom" in the threat model.
- **Project code doing what project code does.** If you ask Commitarium to
  build and run something, it builds and runs it.
- **Backups being unencrypted.** ADR-011 accepts this explicitly: backups are
  checksummed, not encrypted, and must be protected like the projects
  themselves. Provider credentials are excluded rather than encrypted.
- **Local access to an unlocked machine.** Commitarium's state is local and
  readable by the user who owns it. It is not a defence against someone at
  your keyboard, or against other software running as you.
- **Trusting the Docker daemon, the provider CLIs, and the provider accounts
  you connect.** These are trust assumptions, listed as such in the threat
  model.
- **Remote or phone access.** Not built. There is nothing to attack yet.
- **Reports generated by automated scanners** without a demonstrated impact on
  one of the boundaries above.

## What you should know as a user

- **The coordinator and Forgejo bind to loopback only.** Nothing in the stack
  is intended to be reachable from your network.
- **Provider credentials live in local Docker volumes**, one per role, and are
  never transferred by a backup.
- **Backups are not encrypted** and contain your source code, repository
  history and agent conversations.
- **Real providers send your prompts and repository context to that provider**
  under your account and its terms. Commitarium is local-first, not offline.
- **Installers are not production-signed, by design.** The macOS build is
  ad-hoc signed and not notarized; the Windows installer is unsigned. Verify
  you downloaded from the official releases page.
